# HID over I2C

Laptop touchpads, touchscreens and some keyboards sit on an I2C bus and speak
HID over I2C (Microsoft, "HID over I2C Protocol Specification" 1.0). Their ACPI
ids are `PNP0C50` or `ACPI0C50`. This is how OSyx drives them.

## Parts

| Part | Where | Runs |
| --- | --- | --- |
| DesignWare I2C master, HID over I2C protocol, report decoding, `_CRS` resources, description wire format, register-level simulator | `drivers/i2c` (`osyx-i2c`) | host tests, kernel |
| ACPI discovery: `_HID`/`_CID`, `_STA`, `_CRS`, `_DSM`, `SSCN`/`FMCN` through the AML interpreter | `userspace/i2chid` (`osyx-i2chid`), program `i2chidd` | user space, root |
| Claiming controllers, polling threads, input delivery | `kernel/src/drivers/i2c.rs` | kernel |

The kernel never reads AML (see `kernel/src/firmware.rs`): `i2chidd` evaluates
it, encodes the devices (`osyx_i2c::spec`) and calls `firmware(I2C_HID)`. The
kernel decodes and validates the description again, maps the controller
(PCI BAR 0, or an ACPI memory resource that is not kernel RAM), checks the
DesignWare signature (`IC_COMP_TYPE`) and only then talks to a device.

## What is supported

* Controllers: Synopsys DesignWare I2C, Intel LPSS PCI functions (found by
  `_ADR` below a PCI host bridge) and AMD `AMDI0010`/`AMDI0510`
  (ACPI memory resource). 7-bit addressing, standard (100 kHz) and fast
  (400 kHz) mode. SCL timing from `SSCN`/`FMCN`; if the firmware gives none,
  the controller's own reset values are used when plausible, otherwise the
  controller is refused.
* Devices: report descriptor parsed with the USB HID parser
  (`osyx_usb::hid`). Keyboards (modifiers, key arrays, key bitmaps), mice
  (relative X/Y, buttons, wheels) and precision touchpads. Precision
  touchpads start in mouse mode (as the Windows Precision Touchpad
  specification requires), so motion and clicks work without a mode switch;
  a touchpad that reports only contacts gets one-finger pointer motion scaled
  by the pad's physical size, and its button 1 as the left button.
* Power: `SET_POWER ON` and `RESET` at start, `SET_POWER SLEEP` on power off
  and reboot (`drivers::i2c::quiesce`). OSyx has no suspend.

## What is not supported

* **Interrupts.** The device's INT# is a GPIO pin (`GpioInt`) or a global
  system interrupt (`Interrupt`). The kernel has no GPIO controller driver
  (Intel pinctrl, AMD GPIO) and no I/O APIC driver (`arch/apic.rs` handles the
  local APIC and MSI only). Each device is therefore polled: every 4 ms while
  reports arrive, every 16 ms otherwise. Reading the input register consumes
  the report, so an idle poll reads the full `wMaxInputLength` (bus load of
  about 15 % at 400 kHz for a 64-byte report). A device is polled only if it
  answers an empty read by a zero length or a NACK; one that repeats its last
  report is refused, because the pointer would drift by itself.
* Touchscreens (the input core has no absolute events), gestures (tap,
  scroll), consumer-control hot keys, GET/SET_REPORT, output reports (LEDs),
  10-bit addressing, fast-mode plus and high speed, controllers behind PCI
  bridges.

Anything that cannot be driven is logged with its reason and left alone:
`i2chidd: <path>: skipped: ...` (discovery) or `i2c: ... not claimed: ...` /
`i2c-hid <path>: ... not claimed: ...` (kernel).

## Tests

* `cargo test -p osyx-i2c`: DesignWare against a register-level model
  (`osyx_i2c::sim`: FIFO depths, receive-FIFO stall, abort flush, target
  address locked while enabled), protocol, report decoding, resource parser,
  description encoding.
* `cargo test -p osyx-i2chid`: discovery against hand-assembled AML
  (Intel-style and AMD-style machines, every reason to skip a device).
* Kernel self-test `HID over I2C: controller, protocol, input core
  (simulated)`: the same stack on the target build, delivering to the real
  input core (`scripts/test.ps1`).
* `scripts/i2c-hid-test.ps1`: QEMU boot with an extra SSDT (generated by
  `scripts/gen-i2c-ssdt.py`) that adds a touchpad on a controller QEMU does
  not have. Checks that `i2chidd` describes it from the AML and that the
  kernel refuses the missing controller with a reason and claims nothing.

QEMU cannot emulate a DesignWare I2C controller on x86, so **only real
hardware** can show that a laptop's controller behaves like the model, that
its `_DSM`/`SSCN` run on this AML interpreter, and that a given touchpad
passes the idle check and moves the pointer. On a laptop: boot with
`init.args=desktop`, look for `i2chidd:` and `i2c`/`i2c-hid` lines in the
kernel log (`input.log` on the kernel command line logs every event).
